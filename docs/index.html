What is TAS?

TAS means tool-assisted speedrun.

  • You do not play the game live.
  • You write down which keys are pressed at every tiny moment of the game.
  • The tool plays those keys back. It does it exactly the same way every time.
  • You can pause, move forward one moment at a time, go back, and try again.
  • When you are done, the replay looks like a perfect player.

The list of keys is called a script. It is a plain text file that ends in .uktas.

The tiny moment is called a tick. By default one tick is 0.008 seconds, so there are 125 ticks in one second.

How a script turns into ticks

Each line of a script says: "hold these keys for this many ticks". Such a line is called a framebulk.

Words you will see

come back here any time
TAS
Tool-assisted speedrun. A run made by writing inputs and replaying them, not by playing live.
tick
The smallest step of time the tool controls. One tick = one row of input. Default length: 0.008 s.
frame
In this tool, "frame" usually means the same as tick (for example "Step one frame" = one tick).
frametime
How long one tick is, in seconds. host_frametime in the script header sets the default.
script
A text file (.uktas) with a header and a list of inputs. The tool plays it back.
header
The settings at the top of a script, one per line, before the line frames.
framebulk
One input line: "hold these keys, at this angle, for N ticks". It has fields separated by |.
field / column
One part of a framebulk between two | signs. There are 7 or 8.
special frame
A line in the frames list that is not a framebulk, for example look_at, norefresh or FFF. Most take no ticks; save, seed and target_yaw take one tick each.
command
An action in the last field, for example once:bxt_timer_start. once: means "first tick only".
savestate
A snapshot of the whole game at one moment, kept in memory. Load it to jump back to that moment.
slot
A numbered place for a savestate, 0 to 9.
play / pause
Play runs the script. Pause freezes the game so you can look around and step.
step
Advance exactly one tick while paused (F6).
rewind
Go back to tick 0 of the run (F4).
staged input
The keys you hold and the angle you look at while paused. The HUD shows them as STAGED and BULK.
record
Turn what you press into script lines (F10).
branch
An alternative version of the run. "Overwrite from Here" cuts off the frames after the current tick (Restore Branch brings them back). The Branches tab keeps several routes in one project file (.uktasproj).
rank
The game's grade for a level (D, C, B, A, S, P). The HUD level stats show it live. (In the look_at reference, "rank" also means the order in which names are matched.)
seed / RNG
RNG = random number generator. The seed is the number it starts from. Same seed = same "random" events.
deterministic
The same script always gives the same result. This is what makes TAS possible.
desync
When a replay stops matching what happened before. Usually caused by a different start point or setting.
fast-forward
Run the script faster than real time. F7 (hold), the FF button, the ff line or the FFF line.
norefresh
A checkpoint line. Play can jump straight to it instead of replaying everything before it. See Checkpoints & FFF.
yaw / pitch
Where the camera looks. Yaw = left/right. Pitch = up/down. Positive pitch looks down.
look_at
A line that makes the camera aim at an enemy, object or point automatically.
entity / ID
An enemy, projectile or object the tool can aim at. Each one gets a number (ID) when the level loads.
HUD
The text panel drawn over the game with tick, speed, position and more (F12).
toast
A short message in the top-right corner of the screen.
freecam
A free-flying camera that does not move V1 (F2).
autofuncs
Field 1 of a framebulk: helpers like autojump. Leave it as ---------- while you learn.
BepInEx
The mod loader that loads this tool into ULTRAKILL. You install it once (see INSTALL.txt).
config file
BepInEx\config\com.tas.ultrakill.cfg. All settings live there. The TAS window edits it for you.

Your first 10 minutes

install → open → load → play → step

Do these steps in order. Each step says what you should see. If you do not see it, go to Something went wrong?

  1. Install. Install BepInEx 5 (x64) into ULTRAKILL once. Close ULTRAKILL. Open the zip and drag the ultrakill folder onto your ULTRAKILL game folder (the one with ULTRAKILL.exe). Click Replace/merge if asked. The full install notes are in INSTALL.txt next to this file. the folders merge, and BepInEx\plugins\UltrakillTAS\UltrakillTAS.dll exists in your game folder.
  2. Start ULTRAKILL. The first start after installing is slower than usual. That is normal. a message in the top-right corner: "ULTRAKILL TAS Tool 1.2.0 loaded. Insert opens the TAS window."
  3. Enter any level from the game's own menu, for example 1-1. you are playing normally.
  4. Press Insert. the TAS window with tabs: General, Script Editor, Frame Editor, Startup, Keybinds, Overlays, Branches, Recording, Diagnostics, Optimizer.
  5. Load the example. On the General tab, find the Script file card. Click the text box. Type exactly:
    examples\level_load_from_command.uktas
    Then click Load. no red error message under the file list. (You can also click level_load_from_command.uktas in the file list, in the examples group.)
  6. Move the mouse pointer off the TAS window. While the pointer is over the window, the game gets no keyboard or mouse input. nothing yet. This just makes sure your keys reach the game. (If a text box still has focus, your keys stay blocked: press Insert to close the window.)
  7. Press F5 (or click Play). level 1-4 starts loading. After the load, V1 waits, then runs forward by itself. The HUD tick number counts up.
  8. Press F5 again to pause. the game freezes. "PAUSED" appears above the crosshair. The HUD shows a STAGED and a BULK line.
  9. Press F6 a few times. each press moves the game forward by one tick. The HUD tick number goes up by 1 each time.
  10. Look at the HUD (top-left). Press F12 to hide it and again to show it. Then press F11 to stop. after F11 the game is yours again and runs at normal speed.
Done! You loaded a script, played it, paused it and stepped it. Next: write your own script or record one.
Where are the files? Your scripts live in BepInEx\config\ULTRAKILL-TAS\ inside the game folder. The install puts the examples in BepInEx\config\ULTRAKILL-TAS\examples\. In the Script file box, a short path like examples\title_to_level.uktas is looked up inside the script folder first, then in the game's working folder. The file list under the box shows the scripts in that folder and, in a second group called examples, the ones in its examples subfolder: click a name to load it. A full path such as D:\Games\ULTRAKILL\BepInEx\config\ULTRAKILL-TAS\examples\title_to_level.uktas also works.

Your first script

a header, the word frames, then input lines
  1. Open the Script Editor tab. A new file starts with a template like the one below.
  2. Change the lines after frames. Keep the header.
  3. Type a name like my_first.uktas in the editor's File box, then press Ctrl+S to save. A name without a folder is saved in the script folder; .uktas is added if you leave out the extension.the file name in the editor, and no red error line.
  4. Load it in the General tab (type my_first.uktas and click Load), or click Use in TAS in the editor.
  5. Move the pointer off the window and press F5.the level restarts, then V1 does what the lines say.
// my first script
version 1
host_frametime 0.008
seed 0
start_type restart_mission
frames
// autofuncs|movement|actions|frametime|yaw|pitch|frames|commands
----------|------|------|-|0.0|0.0|60|
----------|f-----|------|-|-|-|120|
----------|f-----|j-----|-|-|-|1|
----------|f-----|-1----|-|-|-|1|

What the four lines do: stand still for 60 ticks facing yaw 0, run forward for 120 ticks, jump while running for 1 tick, fire (primary) for 1 tick.

Copy this layout exactly. Movement is 6 characters (f-----). Actions start with the jump slot, then fire: fire alone is -1----, jump alone is j-----. So "fire, no movement" is ------|-1----. The parser accepts some looser layouts, but the layout shown here is the one to copy.

Do this

  • Put start_type restart_mission in every new script. Then every Play starts from the same place.
  • Keep version 1 as the first header line.
  • Use - in the yaw/pitch fields when you do not want to change the angle.
  • Save often (Ctrl+S).

Don't do this

  • Don't leave out start_type. The default is none: the script plays from wherever the game happens to be, so results change from run to run.
  • Don't put | inside a command. It splits the fields.
  • Don't put a 7-character movement field like -------.
  • Don't edit an example file directly. Copy it first.

Comments and saving

Comments start with // or #.

  • The Script Editor keeps your comments when it saves. It writes your text as it is.
  • Saves made from the script in memory drop all comments. These are: stopping a recording, the Frame Editor's Save to Disk, Auto-save to disk, and the General tab's Save button.
If your file has comments you want to keep, edit and save it in the Script Editor.

Recording

F10 turns what you press into script lines

⚠ If a script is loaded, recording writes into that script. Paused inside the run (tick above 0), it cuts off everything after the current tick; at tick 0 (just loaded, not played) it adds the new input after the last frame. When you stop, it saves over the loaded file and drops all comments. Because the file already exists, the tool first asks "Are you sure? Stopping the recording will overwrite your file": Overwrite saves, Cancel keeps recording (paused). If you ticked "Don't ask again until the game closes" earlier, it saves without asking.

Before you record: press New first, or copy the file first. Never record while an example is loaded unless you made a copy.

How recording works

  • F10 (or the Record button) starts recording paused. Nothing moves yet.
  • F5 lets the game run. What you press is recorded tick by tick.
  • F6 records one tick at a time while paused.
  • F10 again (or F11, or the Stop recording button) stops and saves. If the file it saves to already exists, the TAS window opens and asks before overwriting it; the recording stays paused while it asks. Ticking "Don't ask again until the game closes" skips the question (it is shared with the other save buttons).
  • With a script loaded: recording writes into it and saves to its file. Paused at a tick above 0, it records from that tick and drops the frames after it; at tick 0 it records after the last frame of the script.
  • With no script file (empty path): it saves to recording.uktas in the script folder, BepInEx\config\ULTRAKILL-TAS\. This name is the setting Recording file (Overlays tab, card "Startup", box "record file"). An existing recording.uktas is only replaced after you confirm.
  • Loading a script, or clicking New (General tab) or Use in TAS (Script Editor) while recording, ends the recording and saves it straight away, without the overwrite question. Stop with F10 first.

First recording, step by step

  1. Enter a level and open the TAS window (Insert).
  2. In the General tab, Script file card: delete all text in the path box. Then click New. a message "Created a new empty script. Record input or add a frame."
  3. Press F10. a message "Recording into recording.uktas from tick 0. F5 starts, F6 steps." The game is paused.
  4. Move the pointer off the window. Press F5 and play for a few seconds. the game runs. The HUD tick number counts up.
  5. Press F10 to stop. "Saved recording.uktas." and "Recorded N ticks." (If recording.uktas already exists, the window asks first: click Overwrite.)
  6. Rename or copy BepInEx\config\ULTRAKILL-TAS\recording.uktas so the next recording does not replace it.
  7. Load it and press F5 to watch your recording play back.
Tip: to record into a file of your own, type a name such as my_run.uktas in the path box before clicking New. New, Save, Save to Disk, the Script Editor's Save and the end of a recording all put a relative name in the script folder BepInEx\config\ULTRAKILL-TAS\ and add .uktas when the name has no extension. A full path is used as typed. Load looks for a relative name in the script folder first (also trying it with .uktas added), then in the game's working folder.

Recording captures buttons, weapon changes and the mouse wheel. It does not record the menu pointer; menu clicks are written by hand (see Menus).

Aiming at a point or an enemy

HUD → copy → paste after look_at

look_at x y z makes the camera aim at that world point on every tick whose yaw/pitch field is -. To get the numbers:

  1. Overlays tab, HUD panel card: turn on Surface hit coordinate under crosshair (config: HUD: surface hit coordinate, off by default). a HUD line like hit 12.50 3.00 -40.25 (or hit none).
  2. Pause the run and aim the crosshair at the spot you want.
  3. Click Copy hit coordinate (same card). the numbers are now in your clipboard as x y z, for example 12.500 3.000 -40.250.
  4. In the Script Editor type look_at and paste. Put the line above the framebulks that should aim, and use - in their yaw and pitch fields. End with look_at off.
look_at 12.5 3 -40.25
----------|------|-1----|-|-|-|1|
look_at off

To aim at an enemy by ID: turn on Entity inspector (look_at ID under crosshair) in the same card (config: HUD: entity inspector, off by default). Aim at the enemy and read its ID from the HUD. Then write look_at entity <id>. Full details: look_at reference.

01

File shape

header → frames → rows

A .uktas file is a header of key value lines, the single line frames, then framebulks and special frames — one row per line. .hltas is accepted on load.

// header: one setting per line
version 1
host_frametime 0.008
seed 1337
start_type restart_mission
load_command bxt_timer_reset
frames
----------|f-----|------|-|90.0|0.0|20|
----------|f-----|j-----|-|d+2.0|-|1|echo jump

Comments and blank lines

Comments start with // or # — whichever comes first — and run to the end of the line. Blank lines are ignored.

The Script Editor keeps comments when it saves. Saves made from the in-memory script (stopping a recording, the Frame Editor, Auto-save, the General tab's Save) drop them.

Header key separators

A key may be followed by a space, : or =. Only the first token is the key; the rest of the line is the value, so values may themselves contain : or =.

seed: 1337
seed = 1337
description Act 1 any%: no damage
Exactly 7 or 8 fields. The commands field is optional. A command may contain ; but never |, because | is the field separator.
02

It simulates the game's own toss: camera forward × 20 + camera up × 15 + V1's velocity, then gravity and the coin's rigidbody drag, while V1's own path is modelled from the current velocity (gravity while airborne). Ticks in which the coin would touch the level do not count — the game destroys the coin on contact — and each airborne tick scores 1/(1 + distance²), so hovering next to V1 beats drifting away and a longer stay keeps adding. The rest of the bulk keeps the solved angle. It only aims: alt fire (2) still throws the coin.

That is the 3-tick m/m0 pattern and gives the full boost. m1 waits one extra blank tick (4 ticks, half boost), m2 waits two extra blank ticks (5 ticks, quarter boost), and mN waits N extra blank ticks. It never jumps on the release tick: that press would see frame 0 and be a plain jump. It starts the slide again on the landing tick, so the pattern repeats. It works together with s (during the release and blank ticks it stops the autoslide hold); a Slide the framebulk holds itself (field 2 s) cannot be released by an autofunc.
With s and j both on, the landing tick jumps instead of sliding: j presses Jump on that tick, and s does not hold Slide on a tick where the jump goes through.
  • Autofunc letters may be written in any position and are case-insensitive, except S: lowercase s is regular autoslide, uppercase S is spam autoslide. The tool writes each back in slot 3. Any other letter is a parse error.
  • Autofuncs only add presses on top of the script's own input. A button the framebulk holds itself is never released by them.
  • They act while a script plays, and on F6 steps of a paused script. They do nothing while recording or in plain frame stepping without a script.
  • The angle that c or w snaps to is kept by later - angle columns, like look_at.
  • t also writes the tick's angle, but only on the first tick of its bulk, so the blocks after it play with the solved toss angle. e aims on one tick, fires on the next, and is back on your angle after — the game shoots along the camera it read that frame, so a snap and a shot can never share a tick.

G1 — shotgun swap after each shot

On every tick that holds G1 the engine reads the shot from the game state, not from tick timing: the equipped shotgun's gunReady went from true to false since the previous tick, on the same shotgun, with primary fire (1) injected on the previous tick.

The tick that sees the shot presses the variation bind of the equipped variant (y1 / y2 / y3, also written v1 / v2 / v3). The game treats the bind as a fresh equip of that same variation, so the weapon's cooldown resets on the spot: a blue-to-blue swap costs no extra ticks and no slot 2 presses. Then G1 waits for the next shot.

Ticks without a shot keep the script's input.

Hold G1 over the ticks where shots can happen. It does nothing with no shotgun out.

G2 — same-tick shotgun swap

With a shotgun out, fire, select other variant and select original variant are all pressed on this tick, so the cooldown resets with no extra ticks. The swap uses the variant select keys (y1 y2 y3), not next / previous variation.

The other variant is variant 2 when variant 1 is equipped, otherwise variant 1. With another weapon out, slot 2 is pressed first (then variation 1 if slot 2 brought out a later variant) on earlier ticks. A run of G2 ticks starts one sequence, on its first tick.

G2 with primary fire (1) held on the tick before the fire step: Fire1 is released on the fire step's tick and the fire step runs on the next tick, so the game sees a new press. This adds one tick to the sequence.

Timing model

Each tick adds its frametime to a physics accumulator that is spent in native 0.008 s steps (Time.fixedDeltaTime is never changed). A 0.001 tick advances camera and input every tick and physics every 8th; a 0.25 tick runs about 31 steps. The remainder carries across bulks.

0.008one native step per tick
0.01666667two steps per tick
0.001eight ticks per step

Solid blocks are physics steps; dim blocks are ticks with no physics step.

Time scale

The tool never writes Time.timeScale while a TAS runs; ULTRAKILL owns it. A tick advances frametime × the game's current scale of game time, so the game's impact frames, weapon wheel, cutscene slow motion and assist game-speed slider all apply to ticks. The one exception is loading a savestate, which puts the captured scale back.

Hitstop and parry stops (TimeController.HitStop / TrueStop) run their own body and set the scale to 0 themselves. The tool only replaces their WaitForSecondsRealtime with a per-tick timer that calls the game's ContinueTime, so a stop ends on the same tick at any playback speed.

While a TAS runs

Every rendered frame is one tick, and the render rate is capped to speed / host_frametime. A paused or held frame is armed with an almost-zero captureDeltaTime instead of being frozen by the scale.

Savestates

A load restores the saved Time.timeScale, so a state taken in slow motion or at an assist speed comes back at that speed. A state taken inside a hitstop keeps scale 0 and its remaining stop ticks; a live stop the loaded state does not continue is ended through the game's own ContinueTime.

norefresh checkpoints and FFF

norefresh [label] — checkpoint

  • Takes no ticks. The label is optional text.
  • When playback reaches the line, the tool caches the game state there (in memory).
  • The cached state stores the checkpoint tick, script time/path and fixed-step phase. Play resumes at that tick exactly once instead of guessing the boundary.
  • V1 is held by the exact load freeze until the first resumed tick, so the checkpoint is not disturbed between the restore and its input.
  • Next time you press Play, it skips straight to the last valid checkpoint instead of replaying everything above it.
  • A checkpoint is valid only while the header and every line above it are unchanged (comments and spaces do not count), and the same level instance is loaded.
  • Setting: Use norefresh checkpoints (General tab, card "Fast-forward (NoRefresh)"; on by default). Clear norefresh cache forgets them all.
  • Debug: the card's Capture offset slider picks which tick the state is cached on, relative to the marker (0 is the marker's own tick, +1 caches a tick earlier and resumes further behind the script, -1 a tick later and further ahead). Changing it clears the cache so the next Play re-captures.
  • Bake the first frames after a checkpoint (same card, off by default): caching a checkpoint also records the next ticks into a temporary .ukbake in the temp folder, stamped with the script's own hash over that tick range. A resume writes those baked frames over the same ticks first, so the run re-syncs to the recorded trajectory, then continues live. The window is the Sync bake ticks slider (default 30); on a resume, the bake block the checkpoint lands in is also closed automatically when that window ends, as if a bake_end stood there, and the rest of the block plays live. Editing the frames right after the marker changes the hash, so the resume ignores the stale bake. The script and its .ukbake files are never modified; applying baked state marks the run as not submittable.

FFF — fast-forward breakpoint

  • Takes no ticks. Must be alone on its line.
  • Every tick before it runs headless: all cameras off, no 3D rendering, no wall-clock pacing.
  • Rendering comes back on the framebulk right after the marker.
  • Setting: Enable FFF NoRefresh Fast-Forward (same card; on by default).
  • Setting: Pause at the FFF breakpoint (same card; off by default). When on, playback pauses on the exact tick where the fast-forward ends.
  • The card also has "NoRefresh to tick" + Run (fast-forward to a typed tick) and Abort.

Savestates

slots 0–9 · in memory · scene-bound

Slots 0–9, held in memory and tied to the scene they were made in. A rolling ring buffer (default 120 entries) uses the same capture for undo.

What is captured

Player

V1's world transform, local pose and local scale; Rigidbody pose, velocity, angular velocity, gravity, constraints, drag and sleep state; every NewMovement field (dash charge, slide length and direction, slam force, jump/slide timers, framesSinceSlide, grounded/can-jump); the collision capsule's exact shape; camera pitch/yaw; every animator state; and the player's audio/particle state. Values are stored as Unity's floats and as widened double copies, so a load writes back the captured bits rather than a re-derived value.

Player rig

Every ULTRAKILL script under the player, camera, GunControl and FistControl: Revolver, Shotgun, Nailgun, Railcannon, RocketLauncher (charges, heat, cooldowns, napalm fuel and spray state), Punch/FistControl, WeaponCharges (including its cooldown arrays), ground/wall checks, the whiplash hook. Plus the active flag of every weapon/fist object, colliders, Animators (layers, normalized time, parameters, speed, enabled), live particle buffers and audio sources (playing state and position).

Enemies

Every EnemyIdentifier, including inactive, dormant and dead ones. All game scripts on the enemy (attack cooldowns, state enums, targets, child rigs), health, bleed, every Animator with layer/transition/root-motion state, colliders, particle systems with their module configuration, audio sources, Rigidbody state, and every NavMeshAgent and NavMeshObstacle (speed, acceleration, radius, height, avoidance, stopping distance, path, enabled state). A dormant arena actor can wake without replaying from an empty AI state, and a dead ragdoll can be revived or gibbed consistently.

Fire, oil and fluids

Firestarter napalm fuel and spray state, GasolineProjectile droplets, every ground GasolineStain (pose, size, parent, renderer and template), the StainVoxelManager ignition/explosion queues and propagation tick, Flammable fuel/heat/burning/wet state, FireZone and BurningVoxel damage timers and coroutines, Water volumes and their rigidbody/entry lists, Wet wetness, the under-water and dry-zone controllers, and rebuilds for fire/fluid components destroyed after the save.

Doors

Door fields, open/locked/progress flags, BigDoor/SubDoor leaves, handles, NavMeshObstacle, lights, Rigidbody.

Map elements

ObjectActivator, arenas and waves, checkpoints, elevators, platforms, pistons, rotators, switches, breakables, glass, torches, hook points, items, boss bars (fields, enabled, pose, parent), and the active state of every object their triggers or UnityEvents switch.

Projectiles

Coin, Projectile, Nail, Harpoon, Grenade/rocket, Cannonball, Magnet, Explosion, beams.

Effects and coroutines

Trail and line renderers (positions and material settings), audio filter state, live particle buffers and module settings, and the coroutine instances tracked at capture. A load restores the tracked coroutines instead of leaving stale ones running or missing ones stopped.

Randomness, input and physics

The UnityEngine.Random state, every tracked System.Random, every Unity.Mathematics.Random field on a game script (not just SeaBodies), each particle system's seed/auto-seed flag, the full InputSource field state (held, analog and edge/timestamp data), the exact held buttons (with their press edge suppressed), the physics sub-step phase, global gravity/solver thresholds, Physics.simulationMode and the 32×32 layer-collision matrix.

V1 load hold

A savestate restore is not one assignment: enabling objects runs OnEnable, restarts coroutines, updates animators and writes dozens of components around the player. Any of that can move V1 or give his Rigidbody velocity after the player snapshot was written. The load path therefore freezes him before the first restore step:

  • The Rigidbody is made kinematic and its velocity/angular velocity are zeroed.
  • The saved world pose, local pose and Rigidbody pose are re-applied after every restore step and at the end of every paused frame, so an OnEnable, animator update, weapon script or PostRestore cannot leave him a fraction of a unit off.
  • After the full restore, the exact pose, rotation, velocity, angular velocity, Rigidbody flags and sleep state, camera angles and animator state are written back. RNG is restored after that.
  • He stays pinned until the first attempted simulated tick, then the hold is released immediately before that tick's input and physics. Loading while Idle releases at the end of the load frame; stopping, a scene change or another load also releases the old hold.

Saving while a load hold is active temporarily releases it, captures the real dynamic body, then pins the new state again, so the slot never records a kinematic player with zero velocity.

Timers

ULTRAKILL stores cooldowns as TimeSince — an absolute Time.time stamp. On load every stamp is shifted by (now − Time.time at capture), so each cooldown keeps exactly its remaining time.

Input System event timestamps (slideTimestamp, jumpTimestamp) are captured with the surrounding InputSource fields. The later TAS input pass reinstates the held-button mask without generating new press edges.

Delayed calls

ULTRAKILL clears many states with MonoBehaviour.Invoke — Jump() sets jumping/jumpCooldown and schedules NotJumping/JumpReady. Those pending calls are not fields, so the tool reads each script's IL to learn which Invoke("Name", delay) calls it can schedule, records which are pending (IsInvoking) at capture, and on load cancels every such call and re-arms the saved ones.

Without this, a state saved mid-jump restores “jumping = true” with nothing left to clear it: no jump, no ground friction, a jump sound every frame. Computed delays (weapon Shoot/Pump) are re-armed with a default delay.

Death and damage

A state taken while alive revives a dead player on load (DeathSequence ended and switched off, post-processing death effect off, dead=false, ActivatePlayer: camera, weapons and fists back). The hurt screen, the HP/hard-damage flashes and screen-blood overlays spawned after the save are reset or removed. Effect clones held in current…Particle / Drip / Charge fields (slide dust, charge glow) that did not exist at capture are destroyed. Camera, weapon-holder and fist-holder local poses and camera FOV are restored.

Object lists

A Magnet keeps the sawblades, chainsaws, connected magnets and stuck enemies it holds in List<T> fields. Every List<T> whose items are Unity objects is captured as membership and restored (items destroyed since the save are skipped; projectile lists are restored after every projectile exists).

Loaded parts

The state records which scenes are loaded and the rooms that doors stream on and off (Door.activatedRooms / deactivatedRooms), plus the full RoomManager.visitedRooms sequence and RoomArea. A room that was hidden at the save is hidden again on load. If a scene that was loaded at the save is gone now, the load reports it as missing and does not reopen it — reload the level first. Additive scenes loaded after the save are unloaded asynchronously when “Savestate cleanup spawned objects” is on.

Restore order

Active flags first (so OnEnable runs), then values, then effects, then the RNG streams last, so nothing that wakes up during the load can disturb the restored random sequence. NavMesh paths are restored with a synchronous CalculatePath + SetPath, never a queued SetDestination. The saved timeline and fixed-step phase are part of the state: a load knows the tick, script time and script path it belongs to, and aligns Unity's physics phase before restoring.

Orphans

Projectiles and enemies that did not exist at capture are destroyed (setting “Savestate cleanup spawned objects”, default on). Destroyed projectiles are recreated from an inactive template. A destroyed (gibbed or dissolved) enemy is rebuilt from its own template too: the whole saved hierarchy, state and root scale are written onto the new instance, and missing children are rebuilt by name so a limb the game removed after the save comes back in its saved slot. Level objects that were destroyed (broken glass) are counted as missing. Gore objects created after the save (gibs, severed limbs, blood pools, ragdolls) are removed, while objects that existed at capture are kept. Fire, fluid and stain components created after the save are removed the same way.

Not captured

live particle buffers in light rolling-history entries (slots carry them) native-only Unity internals with no public API: exact particle simulation accumulator, blend-tree transition weights, per-collider ignore pairs exact gore geometry and blood decals (gore created after the save is removed; existing decals are not rebuilt) UI element values (the game recomputes them)

Picking Maximize or Minimize for X or Z

  • Face the way V1 should end up travelling. If Facing says +X, the goal is further along +X: Target Position X, Direction Maximize. If it says -X, the goal is further along -X: use Minimize.

  • If Secondary is close to the size of Facing, the route is diagonal. A single axis target will pull it sideways; prefer Speed XZ or a Goal box.
  • Unity convention: yaw 0 looks along +Z and yaw 90 along +X.

  • Only renderers that were off before are touched, and only those are switched off again when the freecam ends or you untick the box. The game's own visibility state is kept.
  • The freecam is separate from the script. It reads your real keyboard and mouse (and ignores them while the TAS window has the focus), and V1 keeps running the scripted pitch, yaw, movement and attacks. Flying the freecam never changes the run.

Baking (bake_start / bake_start_nme / bake_end)

optional sync aid · not legitimate
⚠ Warning

WARNING: BAKING IS NOT LEGITIMATE. Baked playback replays stored state from a previous run and does not prove the inputs produce the run. Runs using baked playback are not valid TAS runs and cannot be submitted. Baking exists only to remove desyncs while you author or verify a route with real inputs.

Baking is an optional sync aid. A bake block records the world state at the end of every tick of a real-input run, so later runs can compare against it or pin the world to it. A script without bake markers is not affected.

11.1 Syntax

bake_start [name] opens a block, bake_start_nme [name] opens the non-map-elements variant, and bake_end closes either one. All are special rows in the frames section (see Special frames), take no ticks and are case-insensitive. The block covers every tick from the row after its start marker up to bake_end.

bake_start room1 ----------|f-----|------|-|90.0|0.0|40| ----------|f-----|j-----|-|-|-|1| bake_end

11.2 Names

One optional token of letters, digits, -, _ and . only; anything else, or a second token, is a parse error. Without a name the block is called blockN (N = 1-based order of bake_start / bake_start_nme in the script). Names are compared case-insensitively and must be unique, because the name is part of the sidecar file name.

11.3 Nesting and parse errors

Blocks cannot nest. These are parse errors (the script does not load):

  • bake_start or bake_start_nme inside an open block
  • bake_end without a matching start marker
  • bake_start or bake_start_nme never closed before the end of the script
  • two blocks with the same name
  • bake_start or bake_start_nme with more than one name, or a name with other characters
  • bake_end followed by anything on its line

A block that covers no ticks is ignored with a warning.

11.4 The hash

Each block has a SHA-256 (lower-case hex) of the canonical header (version, host_frametime, seed, start_type, wait_for_control, load_command, and difficulty / weapons / loadout when set) plus every simulation row from the script start through the block's bake_end, in auto-bulked form. The top-level fist header and every mid-script fist row are deliberately excluded, so adding or changing fist selection does not invalidate a bake; they still count in the norefresh checksum. Markers and pacing rows (bake_start, bake_end, ff, FFF) are not part of it either, so adding, renaming or moving them invalidates nothing. The bake_start_nme mode is included in the hash (normal bake_start hashes are unchanged), so switching a block to or from NME forces a re-record. Any change to an input, angle, frametime, count or command before or inside the block changes the hash; the old bake is then ignored and the block is recorded again on the next run. Existing sidecars made before this rule are accepted through a legacy fist hash when the script still has the matching top-level fist header.

11.5 Sidecar files

One file per block, next to the script: <script>-<block>.ukbake. For example route.uktas with bake_start room1 gives route-room1.ukbake. The file is GZip-compressed (magic UKBK, format version 1) and carries the block's hash and tick count; a file whose hash or tick count does not match the block is not used. An unsaved script cannot be baked.

11.6 Recording

When a block's first tick runs and no valid .ukbake exists, the block is recorded from the real inputs: per tick the time, RNG state, player (position, velocity, angles, health, hard damage, stamina, movement state, weapon, charges), projectiles, enemies, and for a normal block doors and rooms. A bake_start_nme block omits the last two: doors and streamed rooms stay live and are not written to the file. The file is written at the block's last tick. A run that leaves the block early (rewind, load, stop) drops the recording; a block entered mid-way with no bake is not recorded. Status: [RECORDING BAKE].

The Brute-Force Optimizer

Insert → Optimizer tab · inspired by bxt-rs and UniTAS

The optimizer tries thousands of small changes to a chunk of your script and keeps the ones that score better. You describe the goal; it does the grinding.

The idea comes from the TAS optimizer in YaLTeR's bxt-rs and from UniTAS. This is UKTAS's own implementation, built on its savestates and framebulks, so its controls and limits are its own. Everything on this page was read from the code of this build; where a control exists but does nothing yet, the text says so.

What it is and how it works

You pick a segment of the script (a run of framebulks), an objective (for example "highest horizontal speed on the last tick" or "reach this box as early as possible") and optional constraints and boxes. Then START OPTIMIZER repeats this loop:

  1. Baseline. The segment is played once, unchanged. One sample per tick (position, velocity, health) is recorded. Its score is the starting best.
  2. Generate a candidate. The search strategy decides how. Sweep + Random (default) walks one framebulk at a time and adds a random burst when a pass finds nothing. Sweep Only is deterministic coordinate descent: change one thing on one bulk, keep it if better, retry the same bulk, and halve the step when a pass stalls. Random Only mutates 1–4 random bulks from the current best, with the small restart/top-5 chances. Adaptive ML uses a UCB1 bandit to choose which mutation operator to spend attempts on and breeds an elite pool by crossover.
  3. Evaluate the physics. The tool restores the savestate taken at the segment start, plays the candidate to the end tick and samples every tick. Dying ends the attempt early.
  4. Validate. A candidate is thrown away (and counted as invalid) if V1 died, touched a Keep-Out box, missed a Waypoint box, or broke a constraint.
  5. Lock improvements. A valid candidate that scores better than the current best (by more than 0.000000001) replaces it. Nothing worse is ever accepted.

Your script file is not touched while this runs: the candidate is swapped in memory and the original is put back when the run ends. Nothing is written until you press an apply or save button (Saving the result).

Core Eject nuke boosts

Fire a shotgun core, then shoot or parry it so the blast launches V1. Aim lock keeps the shot on the moving core while the timing changes.

Slide-jump speed

Maximize speed_xz on the last frame and let it tune when the slide, jump and dash start.

Corner cutting

A Goal box past the corner, Keep-Out boxes on the walls, objective Reach Goal Box.

Coin toss timings

Let it move the tick counts around a coin throw and shot. Aim lock re-aims at the coin each attempt.

Tight doorway movement

Keep-Out boxes on the frame, a Waypoint in the opening, a Goal box behind it.

Before you start

  • A script must be loaded and playing. The tab refuses to start otherwise (Optimizer: no script loaded., press Play so playback can reach the start tick.). Playback has to reach the start tick; the optimizer begins there.
  • Start and End must sit on framebulk boundaries. If a tick falls in the middle of a framebulk, split it first (Frame Editor → Split Bulk). End Tick is exclusive: the framebulk that starts at End Tick is not optimized.
  • The segment keeps its total length. Applying a result that has a different number of ticks is refused, because it would shift every later tick.
  • Pausing, stopping or leaving playback ends the run and puts your script back. If playback has already gone past the start tick when the run begins, it stops with Playback passed the start tick before the optimizer began. Rewind and start again.
  • The Single-Frame Mode (splitting bulks into 1-tick frames) is not implemented. The tab says so.

SSJ detection

An SSJ is a jump made while recovering from a ground slide. In the game code, StopSlide() sets framesSinceSlide = 0, and FixedUpdate() increments it while V1 is not sliding. Jump() calls TrySSJ(), which accepts 0 < framesSinceSlide < ssjMaxFrames (the shipped ssjMaxFrames is 4, so frames 1, 2 and 3). The quality is 1 / 2^(frame-1): the first possible frame gives the full boost, then half, then a quarter. The wiki’s values are +24.75, +12.375 and +6.1875 u/s.

Jumping out of a held slide is not an SSJ. Jump() calls StopSlide() before TrySSJ(), so that jump sees framesSinceSlide = 0. You must release slide, let one or more ticks pass, then jump. The optimizer looks for exactly that: a new jumping edge while the previous sample was grounded, with framesSinceSlide 1–3 and sliding false. Requiring the previous sample to be grounded keeps ordinary wall jumps out, since those start from the wall instead of the ground. The SSJ Boost target rewards the detections; normal Speed XZ and Reach Goal Box runs also benefit because the game applies the boost to horizontal velocity. The m/m0 macro emits the perfect 3-tick input pattern; m1 and m2 deliberately add blank ticks for the weaker recovery frames.

The Spatial boxes (freecam) card is the first card in the tab, and Geometry awareness follows it. Boxes are covered in 12.2.

Control and telemetry

  • START OPTIMIZER begins the search (it turns into STOP OPTIMIZER while running). Stop keeps the best route found so far.
  • Clear Paths removes the white baseline, cyan current-best and dark-teal candidate lines from the 3D view. The boxes and the best segment stay; new attempts can draw a candidate again.
  • Two lines update live: 
    Speed: 12.3 it/s (40% invalid) | Attempts: 500
Baseline: 812.4 -> Best: 861.9 (Delta: +49.5)
    it/s is attempts per second, % invalid is the share thrown away by death, boxes or constraints, Attempts is the total tried, Baseline is the unchanged segment's score, Best the current best, and Delta their difference.
  • Below them, up to 10 log lines: Baseline score: ..., Found new best value: ... (delta: ...), and warnings such as Baseline is invalid (...); searching from it anyway. An invalid baseline still gives a start so the search can climb back to a valid route.
  • In Adaptive ML, extra lines show generation and population, top operators, elite consensus and differential trend, and stagnation progress. These are diagnostics, not a promise that the search has found the global best.

Projectile and coin aim lock

"Lock Shots to Airborne Projectiles/Coins" · on by default

When you change the timing of a throw, the grenade or coin is somewhere else, and a fixed yaw/pitch misses it. The aim lock fixes that: in every attempt, the shot is re-aimed at the projectile where it actually is.

  1. Baseline tagging. During the first (unmodified) attempt, on the first tick of every framebulk that holds fire (1), alt fire (2) or punch (p), the tool looks for the nearest live airborne projectile and tags it to that framebulk's ordinal (its position in the list of framebulks inside the segment: first, second, third...). The script's own aim is kept for the baseline.
  2. Candidate aiming. In later attempts, on the first tick of that same framebulk, the camera is pointed from V1's camera at the tagged projectile: the same instance if it is still alive, otherwise the nearest of the same type. Ordinals survive tick-count changes, which is why they are used and not tick numbers.
  3. If no tagged projectile exists on that tick, or the framebulk does not fire, the framebulk's own yaw and pitch are used.

Writes only the winning segment, with the script's header copied over, to optimization-best.uktas in the scripts folder. Your loaded script is not changed.

Save as New Branch

Builds the complete route (your script with the best segment spliced in).

  • With a .uktasproj project open: adds a branch named Optimized @<StartTick> that diverges from the active route at the Start Tick, makes it the active branch, and rewrites <name>-bridged.uktas next to the project so the TAS player loads it. Switch routes any time in the Branches tab.
  • No project open: saves the full route next to the script as <name>_optimized.uktas.

Which to pick

Use Save as New Branch when you want to keep your old route for comparison; the project compares routes by total simulation time. Use Apply Best when you are happy to overwrite. Use Save Best to File to inspect the framebulks first.

Video recording and FFmpeg commands

Recording tab · header keys · script commands

The recorder renders the run offline: playback stays frame-locked (one tick per rendered frame), every frame is piped to FFmpeg, and game audio is captured on request. Motion blur comes from camera poses interpolated between ticks. ffmpeg.exe is not shipped; the tool looks for it in the configured ffmpeg path, then the game folder, then every PATH entry. Missing: ffmpeg not found. Set its path in the Recording tab.

Baked inputs in a render. The Recording tab has Record TAS playback with baked inputs (NOT LEGIT). Turning it on enables baked playback for that render and starts the run if needed; the video is marked NOT LEGITIMATE and is not submittable. Performance Render Mode is suspended while any video is recording and restored when the recording ends.

What the tool runs

The video is piped from the game as raw RGBA frames. The window size is rounded down to an even number of pixels.

ffmpeg -y -f rawvideo -pix_fmt rgba -s <W>x<H> -r <fps> -i - -vf vflip -c:v libx264 -preset medium -crf 16 -pix_fmt yuv420p "<out.mp4>"

With Record audio on (the default), the video goes to a temporary .video.mp4 and the sound to a .audio.wav; when the recording stops they are joined, the video stream copied untouched and the sound normalized to -14 LUFS, then scaled by record_volume:

ffmpeg -y -i "<video>" -i "<wav>" -map 0:v -map 1:a -c:v copy -af "loudnorm=I=-14:TP=-1.5:LRA=11,volume=<vol>" -ar 48000 -c:a aac -b:a 320k "<out.mp4>"

If the join fails, the video alone becomes the output and the WAV file is kept. FFmpeg gets 2 minutes to finish when the recording stops.

Recording from the freecam

The recorder films what the game window shows. In the freecam that is the freecam view, so you can record a third-person shot of the run. Turn on Show V1 playermodel in freecam if you want V1 in the shot; otherwise the body stays hidden. Camera interpolation for motion blur is first-person only: in the freecam and in third person, the real frame is used for every sub-frame, so there is no extra blur from camera movement. "Clean render while recording" (on by default) hides the TAS HUD, hitboxes, triggers and trajectory, and shows the viewmodels.

look_at — how aiming works

takes 0 ticks · drives - columns

look_at points the camera at something on every tick until it is turned off. It never consumes a tick, and it only ever drives a - angle column.

The four forms

look_at entity 12 head 0 0 0
^^^^^^^ ^^^^^^ ^^ ^^^^ ^^^^^^^
   |       |    |    |      |
   |       |    |    |      +-- offset   ox oy oz, world units, optional
   |       |    |    +--------- hitbox   name or alias, optional
   |       |    +-------------- id       stable number 1..N, or 10000+
   |       +------------------- keyword  "entity": aim at an ID
   +--------------------------- statement
FormMeans
look_at entity <id> [hitbox] [ox oy oz]One specific entity, by its level ID.
look_at <type|category> [hitbox] [ox oy oz]The nearest live match by name — a component type, an enemy type, a GameObject's own name, or a category (enemy, projectile, object).
look_at <x> <y> <z>A fixed world coordinate.
look_at offStop aiming; - columns keep the last aimed angle.

Three plain numbers are a point

look_at 12 0 0 aims at x = 12, not at entity 12. A name can never be all digits, so the forms cannot collide.

Offset is always last

Hitbox, then three numbers. look_at coin 0 1 0 is a coin one metre up; look_at v2 head 0 0 0 is V2's head.

The three categories

look_at
 |
 +-- enemy ....... 38 types ... EnemyIdentifier and its subclasses
 |                filth, stray, schism, soldier, …
 |
 +-- projectile .. 12 types ... projectile, coin, nail, harpoon, …
 |

enemy, projectile and object are valid names themselves — look_at enemy aims at the nearest enemy of any type. They rank last on the matcher's ladder, so an exact type or an object's own name wins over a category.

Nothing else in the scene is matchable by name — doors, checkpoints, arenas, hook points, props. For those, aim at a coordinate: look_at 10 5 -20.

Only live, active objects

A pooled coin or a dormant wave enemy is invisible to the search. The player's own hierarchy is excluded.

The pick is pinned

The winner is reused every tick while it stays alive and active. When it dies or deactivates, the next tick picks again. A state load, a rewind past the pick, or a norefresh resume forgets the pick and resolves from the restored state.

A toast names what was picked — look_at v2: entity 127 (V2Second, 12.4 m away). — so the ID can be written into an explicit look_at entity 127 line.

What the angles become

                     o  target point (center or hitbox, plus offset)
                    /|
                   / |  dy
                  /  |
     camera  x---+---+  horizontal = sqrt(dx² + dz²)
              dx,dz

   pitch = -atan2(dy, horizontal)      positive pitch = DOWN
   yaw   =  atan2(dx, dz) * rad2deg    0 = +Z, 90 = +X

Yaw is unwrapped to the turn nearest the previous yaw, so a target behind you never spins the camera 360°. Looking straight up or down has no yaw of its own and keeps the current one. Both angles are computed at the start of each tick and written into the same yaw/pitch the framebulk columns use, so recording, savestates and the HUD all see them.

Explicit angles win for their tick. An absolute value, a relative d+/d-, or a target_yaw line overrides the aim for that tick; the look_at stays armed and applies again on the next - tick. It also takes priority over a running change yaw|pitch. After look_at off, - columns keep the last aimed angle.

Entity IDs

When a level loads, every enemy (EnemyIdentifier), projectile (Projectile, Coin, Nail, Harpoon, Grenade, Cannonball, Magnet, GasolineProjectile, Landmine, ThrownSword, BlackHoleProjectile, Chainsaw) and object (ItemIdentifier, Breakable) in the scene — active or not — is sorted by type name, then hierarchy position, and numbered 1..N.

The list is built from the level scene's own hierarchy on its first visible frame, never later in the run, so objects that spawn or die during play cannot shift the numbers: the same level gets the same IDs on every load, and savestates keep them. Objects spawned later get IDs from 10000 in the order the entity inspector first sees them; those are not reproducible across runs, so scripts should use IDs below 10000. Read IDs from the HUD's entity inspector. It is off by default: turn on Entity inspector (look_at ID under crosshair) in the Overlays tab, card "HUD panel" (config HUD: entity inspector).

For a fixed point, turn on Surface hit coordinate under crosshair in the same card, aim the crosshair, click Copy hit coordinate, and paste after look_at: look_at x y z aims the camera at that point.

----------|f-----|-1----|0.008|-|-|1|         // and shoots it

Hitbox names

optional second token

A hitbox selects a point on the target instead of its center. Names are matched against active child colliders, child transforms and EnemyIdentifier limbs.

NamePoint
(nothing)Center of the active collider bounds.
centerThe same center.
bodyThe same center.
torsoThe same center.
chestThe same center.
middleThe same center.
headThe game's weakPoint if it is active, else the first active child named or starting with “head”.
weakpointThe same weakPoint lookup.
anything elseThe first active child collider, child transform or limb whose name equals it — or starts with it when the alias is 3+ characters.

Normalization

Only letters and digits are kept, lowercased. So left_arm, Left Arm, left-arm and LeftArm are one name, and head also matches head01. Aliases shorter than 3 characters must match exactly.

Search order

Child colliders (center of their bounds) → child transforms → EnemyIdentifier.limbs (limbs can sit outside the enemy's hierarchy and point back at it). A hitbox that is not present on a live target holds the angle and reports exactly one warning.

Practical advice. head is the one alias with a special rule and the one worth remembering: aim head for headshots, leave the hitbox out for the body — the transform pivot is at the feet for most enemies.
